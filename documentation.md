## Activation Quantization: Static vs Dynamic, GEMM vs GEMM-Int

In **dynamic** mode, activation scales (and zero-points for asymmetric) are computed per-token at inference time: each token's activation row gets its own scale derived from its actual min/max. This gives optimal quantization but requires runtime computation. In **static** mode, scales are precomputed once during calibration (`calibrater/calibrate_act_scales.py`) by observing activations across many calibration tokens. The calibrator records per-column min/max statistics across all tokens, then derives a single (scale, zero) pair per column that covers the full observed range. These are saved to disk and loaded at inference time — no per-token computation needed.

The critical difference between **standard GEMM** and **integer GEMM** (`--int_gemm`) is how scales interact with the dot product. In standard (float) GEMM, quantized activations are immediately dequantized back to float before the matmul, so per-column scales work fine — each column's scale multiplies independently. In integer GEMM, the multiply-accumulate happens in integer arithmetic inside hardware accumulators of limited width (`--acc_bits`). Scales cannot be applied per-column because they'd need to factor out of the integer dot product, which is impossible when each column has a different scale. Instead, static int_gemm uses **per-group** scales where one scale covers `acc_block_k` consecutive columns — exactly one accumulator block. This way the scale factors out of each block's partial sum. The per-group (scale, zero) is derived from the per-column calibration data by taking the min/max of the representable ranges within each group. For **asymmetric** quantization (non-zero zero-points), the zero-point correction is precomputed as a constant `[N]`-dimensional bias vector (`static_zp_bias`) at setup time and added after the integer kernel — no kernel modifications needed.
